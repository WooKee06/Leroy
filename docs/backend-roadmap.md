# План разработки бэкенда Leroy

Дата: 11.11.2026
Связанные документы: `docs/client-audit.md`
Репозитории: клиент `Leroy/`, сервер `LeroyServer/`

Документ отвечает на два вопроса: **с чего начать прямо сейчас** и **в каком порядке идти дальше**. Каждая фаза — это законченный кусок, который можно задеплоить и проверить, а не «половина фичи».

---

## 0. Как читать план

- Фазы идут строго по зависимостям: нельзя сделать оплату балансом без кошелька и нельзя безопасно делать кошелёк без транзакций в заказах.
- Внутри фазы задачи упорядочены сверху вниз.
- `[ ]` — задача не сделана, отмечай `[x]` по мере выполнения.
- Для каждой фазы есть **критерий готовности** — если он не выполнен, фаза не закрыта.
- Оценки в днях — для одного разработчика, без учёта ревью и деплоя.

**Главный принцип:** сначала деньги и целостность заказа, потом доставка, потом продавец, потом «красота» (уведомления, админка, загрузки). Не начинать с админки, аналитики и уведомлений — они не разблокируют ничего.

## 2. Фаза 0 — фундамент и критические баги (1–2 дня)

Без этого нельзя безопасно менять схему и включать реальные деньги.

### 0.1. Миграции вместо `synchronize`

Сейчас в `LeroyServer/src/app.module.ts` стоит `synchronize = DATABASE_SYNCHRONIZE !== 'false'` (по умолчанию `true`), а `src/config/data-source.ts`, на который ссылается `package.json`, отсутствует. Для новых таблиц кошелька это опасный режим.

- [ ] Создать `src/config/data-source.ts` (Postgres, те же env, `entities`, `migrations: ['src/migrations/*.ts']`, `synchronize: false`).
- [ ] Сгенерировать baseline-миграцию по текущей схеме: `npm run migration:generate -- src/migrations/Initial`.
- [ ] Прогнать `npm run migration:run` на локальной БД, убедиться, что схема не меняется.
- [ ] В `app.module.ts` по умолчанию поставить `synchronize: false`.
- [ ] В Render добавить `DATABASE_SYNCHRONIZE=false`, миграции запускать перед стартом приложения (release command или `npm run migration:run && node dist/main`).

### 0.2. Выключить мок-оплату в проде

- [ ] Добавить env `PAYMENTS_MOCK_ENABLED` (по умолчанию `false`).
- [ ] В `payments.service.ts` при `provider = mock` и выключенном флаге бросать `ServiceUnavailableException`.
- [ ] Оставить флаг включённым только в dev/тестовом окружении.

### 0.3. Мелкие, но важные баги (по 5–20 минут каждый)

- [ ] Клиент: в `src/shared/lib/orders.ts` заменить `"canceled"` на `"cancelled"` (сервер отдаёт `cancelled`).
- [ ] Сервер: в `orders.service.ts` присвоить `savedOrder.deliveryPrice = deliveryPrice` перед сохранением (сейчас в БД 0, а в `total` доставка уже входит).
- [ ] Сервер: согласовать провайдера Stars — клиент отправляет `"telegram_stars"`, enum `"stars"`. Принимать оба или исправить клиент.
- [ ] Клиент: `OrderDetailPage` использовать `GET /orders/:id` вместо загрузки всех заказов и поиска в массиве.
- [ ] Клиент: «2 адреса» в `ProfilePage` заменить на `addressStore.count`.
- [ ] Сервер: проверять при создании отзыва, что товар куплен и заказ в `delivered/completed` (сейчас проверяется только дубликат).
- [ ] Сервер: вызывать `BotService.notifyNewOrder` / `notifyOrderStatusChanged` / `notifyNewReview` (методы уже написаны, но не используются).

**Критерий готовности фазы 0:** `npm run migration:run` работает на чистой БД, `synchronize=false`, прод-сборка стартует, мок-оплата выключена флагом, перечисленные баги закрыты.

## 3. Фаза 1 — Кошелёк, ledger и оплата балансом (5–7 дней)

Это ядро. После неё «Официальный баланс» перестаёт быть фикцией, а возвраты и выплаты получают фундамент.

### 3.1. Сущности

Создать в `LeroyServer/src/entities/`, зарегистрировать в `index.ts`:

```
Wallet
  id uuid
  userId uuid unique
  available decimal(12,2) default 0
  hold decimal(12,2) default 0
  currency varchar default 'RUB'
  version int  // optimistic lock
  createdAt, updatedAt

WalletTransaction   // append-only ledger
  id uuid
  walletId, userId
  type: topup | purchase | refund | payout | commission | bonus | adjustment
  amount decimal(12,2)      // со знаком: + пополнение, − покупка
  balanceAfter decimal(12,2)
  status: pending | completed | failed | reversed
  referenceType: order | payment | topup | refund | payout
  referenceId uuid
  idempotencyKey varchar unique nullable
  meta jsonb
  createdAt

TopUp
  id uuid
  userId uuid
  amount decimal(12,2)
  provider: manual | ton | stars | card
  status: pending | completed | failed | expired
  externalId varchar nullable
  expiresAt timestamptz
  createdAt, completedAt
```

Правки существующих сущностей:

- `Payment`: добавить `BALANCE` в `PaymentProvider`, поля `idempotencyKey`, `failureReason`.
- `Order`: см. фазу 2, но `paymentId`/`paidAt` удобно добавить уже здесь.

### 3.2. Сервис

`WalletService` (`src/modules/wallet/`):

- [ ] `getWallet(userId)` — создать кошелёк лениво, вернуть `{ available, hold, currency }`.
- [ ] `credit(userId, amount, type, reference, idempotencyKey, manager?)` — только внутри транзакции.
- [ ] `debit(...)` — проверка `available >= amount`, иначе `BadRequestException("Недостаточно средств")`.
- [ ] Все изменения — через `WalletTransaction`; поле `balanceAfter` считается в той же транзакции.
- [ ] Повтор с тем же `idempotencyKey` возвращает существующую операцию, а не создаёт новую.
- [ ] Запрет отрицательного баланса (кроме админской корректировки с явным флагом).
- [ ] Блокировка строки: `SELECT ... FOR UPDATE` по `walletId`, чтобы два параллельных списания не увели баланс в минус.

### 3.3. Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/wallet` | баланс и холд |
| GET | `/api/wallet/transactions?limit=&cursor=` | история операций |
| POST | `/api/wallet/topup` | создать пополнение (пока `manual`/тестовое) |
| POST | `/api/wallet/topup/:id/confirm` | подтвердить пополнение (для dev/админа; позже — вебхук провайдера) |
| POST | `/api/payments` | добавить `provider = balance`: атомарно списать и пометить заказ оплаченным |

Порядок оплаты балансом:

1. Проверить, что заказ принадлежит пользователю и в статусе `pending`.
2. Открыть транзакцию.
3. Заблокировать кошелёк, проверить баланс.
4. Списать `order.total` → `WalletTransaction(type=purchase)`.
5. Создать `Payment(provider=balance, status=completed)`.
6. Перевести заказ в `paid`, проставить `paidAt`.
7. Закоммитить.

Любая ошибка на шаге 4–6 — полный откат, баланс не меняется.

### 3.4. Клиент (параллельно, после появления эндпоинтов)

- [ ] `accountStore`: убрать локальный `balance`/`topUp`, тянуть `GET /wallet`.
- [ ] `BalancePage`: `topUp` → `POST /wallet/topup`, показывать историю операций.
- [ ] `checkoutStore`: при `paymentMethod = "balance"` вызывать `POST /payments` с `provider: "balance"`.
- [ ] `PaymentMethodsPage`: «Официальный баланс» — реальный, остальное «скоро».

### 3.5. Критерии готовности

- [ ] Пополнение на 1000 ₽ → баланс 1000, одна запись в ledger.
- [ ] Оплата заказа на 800 ₽ → баланс 200, заказ `paid`, запись `−800`.
- [ ] Повторный запрос с тем же `idempotencyKey` не списывает второй раз.
- [ ] Два параллельных платежа на 800 при балансе 1000 → проходит один, второй получает 400.
- [ ] Недостаточно средств → 400, баланс и заказ не меняются.
- [ ] Пополнение и оплата покрыты e2e-тестом.

## 4. Фаза 2 — Целостность заказа (3–4 дня)

Нужна до включения реальных денег, иначе возможны двойные заказы и oversell.

- [ ] Обернуть `createOrder` в транзакцию (`DataSource.transaction`).
- [ ] Заблокировать товары `SELECT ... FOR UPDATE` перед проверкой стока.
- [ ] Поддержать `Idempotency-Key` (заголовок или поле DTO): повторный запрос возвращает тот же заказ.
- [ ] Списывать сток и увеличивать `salesCount` в той же транзакции, что и создание заказа.
- [ ] Добавить недостающие поля в `Order`:
  - `deliveryPrice` (заполнять!), `deliveryProvider`, `deliveryTariff`
  - `pickupCode`, `pickupAddress`
  - `trackingNumber`, `deliveryStatus`
  - `paidAt`, `shippedAt`, `deliveredAt`, `cancelReason`
- [ ] Добавить `OrderEvent` (таймлайн: создан, оплачен, принят, отправлен, доставлен, отменён).
- [ ] Валидировать переходы статусов (разрешённая карта переходов) для заказа и `SellerOrder`.
- [ ] Добавить `POST /api/orders/:id/cancel` (покупатель до отправки; возврат на кошелёк, возврат стока).
- [ ] Джоб автоотмены неоплаченных заказов через N минут.
- [ ] Пересчитывать `Store.orderCount` при оплате.

**Критерий готовности:** двойной `POST /orders` создаёт один заказ; искусственная ошибка посередине не оставляет частичный заказ; два покупателя на последний товар — второй получает понятную ошибку; отмена возвращает деньги и сток.

## 9. Порядок и зависимости

```
Фаза 0 (фундамент)
   └─> Фаза 1 (кошелёк + баланс)
          └─> Фаза 2 (транзакции заказа, статусы, отмена)
                 ├─> Фаза 3 (СДЭК, тарифы, ПВЗ, вебхуки)
                 └─> Фаза 4 (продавец, выплаты, аналитика)
                        └─> Фаза 5 (уведомления, админка)
                               └─> Фаза 6 (загрузки, контент, мелочи)
```

Фазы 3 и 4 можно вести параллельно после фазы 2.

## 11. Definition of Done для любой фазы

- [ ] Обновлён `docs/client-audit.md` или этот файл (что перестало быть моком).

## 12. Риски

| Риск | Что делать |
|---|---|
| `synchronize=true` в проде | Фаза 0, не начинать без неё |
| Деньги без ledger | Любые изменения баланса только через `WalletTransaction` |
| Oversell и двойные заказы | Транзакции + `FOR UPDATE` + `Idempotency-Key` (фаза 2) |
| СДЭК недоступен | Fallback-тариф из env, но не хардкод в коде |
| Потеря загрузок при редеплое | S3 до запуска отзывов с фото в проде |
| Мок-оплата осталась включённой | Флаг по умолчанию `false`, проверка в health/старте |

## 13. Что НЕ делать сейчас

- Не начинать с админки, уведомлений, i18n, подарков и красивой аналитики.
